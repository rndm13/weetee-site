## 1. Сфера дії

Модель охоплює вебсайт для опису програмного забезпечення й публікації документації, форумні обговорення, автентифікацію користувачів та адміністративні функції, що впливають на облікові записи, ролі й контент.

До сфери аналізу входять:

- клієнтський браузер і frontend-ресурси, зібрані Vite;
- HTTP-рівень Laravel: маршрути, контролери, middleware, валідація та механізми автентифікації/авторизації;
- модулі Authentication, Forum, Administration та публічний контент;
- PostgreSQL та дані застосунку;
- репозиторій, Composer/npm-залежності, конфігурація й релізні артефакти;
- журнали, резервні копії та канали адміністрування, якщо вони існують у розгортанні.

Поза безпосередньою моделлю: фізична безпека хостингу, внутрішня реалізація постачальника інфраструктури й внутрішні системи сторонніх провайдерів. Їхні зовнішні інтерфейси та доступність секретів усе одно враховуються як залежності.

## 2. Припущення та обмеження

1. Вебзастосунок приймає HTTP-запити та використовує PostgreSQL для частини даних.
2. Форум містить користувацький текст, який зберігається і згодом відображається іншим користувачам.
3. Частина операцій потребує автентифікації, а адміністративні операції мають бути доступні лише суб'єктам із відповідними правами.
4. Laravel використовується як основний серверний фреймворк; конкретні guards, middleware, Policies/Gates і драйвер сесій не підтверджені.
5. Приймання файлів, зовнішня пошта, API-токени, CAPTCHA, аналітика й фонові черги не підтверджені. Загрози для них позначаються умовними.
6. Наявність резервного копіювання, централізованого моніторингу, WAF, reverse proxy, CI/CD і окремого адміністративного мережевого контуру не підтверджена.
7. Модель аналізує вебрівень і межі довіри, а не виконує penetration test чи аудит налаштувань.

Припущення слід замінити перевіреними фактами під час технічного review. Якщо якась функція відсутня, пов'язані з нею загрози позначаються як непридатні, а не як підтверджені вразливості.

## 3. System Overview

Система приймає запити користувачів через браузер. Laravel обробляє запити, викликає перевірки доступу та працює з PostgreSQL. Ресурси frontend компілюються Vite. PHPUnit використовується для автоматизованого тестування, але тестова інфраструктура не є production-компонентом і має бути ізольована від production-секретів та даних.

|---|---|---|---|

| D2 | Data Store | Конфігурація та секрети | `.env`, середовищні змінні, ключі та облікові дані залежностей; точне місце зберігання не підтверджене. |
| D3 | Data Store | Журнали й резервні копії *(якщо ведуться)* | Операційні та діагностичні записи, потенційно чутливі дані; доступ має бути обмежений. |
| D4 | Data Store | Репозиторій і lock-файли | PHP/JS-код, конфігурація, міграції, тести та історія змін. |
| F1 | Data Flow | Браузер ↔ Laravel через HTTP(S) | URL, параметри, cookies, сесійні ідентифікатори, форми та відповіді. У production має використовуватися HTTPS. |

### 3.2 Trust Boundaries

| ID | Межа довіри | Що перетинає межу | Основні вимоги |
|---|---|---|---|
| TB1 | Користувацький браузер ↔ сервер Laravel | HTTP-запити, cookies, поля форм, URL-параметри й відповіді | HTTPS, серверна валідація, CSRF-захист для браузерних мутацій, rate limiting, екранування виводу, безпечні cookies. |
| TB2 | Laravel ↔ PostgreSQL | SQL і дані застосунку | Параметризовані запити, мінімальні права DB-акаунта, обмеження цілісності, мережеве обмеження доступу до БД. |
| TB3 | Звичайний користувач ↔ адміністративні функції | Запити до privileged endpoints | Серверна перевірка ролі й дозволу на кожну операцію; відмова за замовчуванням; аудит критичних змін, якщо підтримується. |
| TB4 | Вихідний код/залежності ↔ середовище збірки/production | Код, npm/Composer пакунки, налаштування й релізні артефакти | Перевірка походження/вразливостей залежностей, контроль доступу до гілок, захист секретів, повторювана/контрольована збірка. |
| TB5 | Застосунок ↔ логи/резервні копії | Технічні події та збережені дані | Мінімізація чутливих полів, контроль доступу, обмежене зберігання й перевірка відновлення. |
| TB6 | Laravel ↔ зовнішня пошта | Поштові повідомлення або інші інтеграції | Мінімальний обсяг переданих даних, TLS, секрети ззовні коду, обробка помилок та обмеження довіри до відповіді постачальника. |

## 5. STRIDE Analysis

STRIDE використовується для класифікації загроз: **S** — Spoofing (підміна особи), **T** — Tampering (модифікація), **R** — Repudiation (заперечення дій), **I** — Information Disclosure (розкриття інформації), **D** — Denial of Service (відмова в обслуговуванні), **E** — Elevation of Privilege (підвищення привілеїв).

### 5.1 Канонічна відповідність типам елементів DFD

| DFD Element | S | T | R | I | D | E |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| External Interactor | ✓ |  | ✓ |  |  |  |
| Data Flow |  | ✓ |  | ✓ | ✓ |  |
| Data Store |  | ✓ |  | ✓ | ✓ |  |
| Process | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

Категорії не є взаємовиключними. Наведена відповідність — інструмент для пошуку загроз, а не гарантія, що кожна категорія обов'язково реалізується для кожного елемента.

### 5.2 Загрози за елементами системи

| DFD Element | STRIDE | Загроза для порталу | Основні заходи / перевірки |
|---|---|---|---|
| E1/E2: External Interactor — відвідувач або користувач | S | Зловмисник використовує викрадені облікові дані або вкрадену сесію, щоб діяти від імені користувача. | Безпечне хешування паролів, rate limiting, HTTPS, безпечні cookies, регенерація сесії після входу, процедура завершення сесій. |
| E1/E2: External Interactor | R | Користувач заперечує виконання дії, а система не має достатньо даних про критичну операцію. | Для критичних адмін-дій — мінімальний аудит: актор, дія, ціль, час і результат; не журналювати секрети. |
| E3: External Interactor — адміністратор/модератор | S, R | Компрометація привілейованого облікового запису або неможливість встановити, хто виконав адміністративну дію. | Мінімальні привілеї, захист акаунтів, повторна перевірка дозволу на сервері, аудит критичних дій; MFA розглянути, якщо підтримується інфраструктурою. |
| P1: Process — браузер/frontend | T, I | Зловмисний скрипт або помилкова клієнтська логіка змінює запит/читає дані, доступні в контексті браузера. | Не довіряти UI; екранувати користувацький контент; уникати секретів у bundle; відповідні CSP/security headers після перевірки сумісності. |
| F1: Data Flow — браузер ↔ Laravel | T | Поля запиту змінюються: клієнт підставляє інший `author_id`, `role`, `status` або ID ресурсу. | Серверна валідація, заборона масового присвоєння привілейованих полів, перевірка власності та дозволів для кожного ресурсу. |
| F1: Data Flow | I | Сесійні cookies, паролі або дані форм перехоплюються через незахищене передавання чи витікають у URL/логи. | HTTPS у production, безпечні cookie-параметри, POST для секретних даних, відсутність секретів у логах та URL. |
| F1: Data Flow | D | Велика кількість запитів або дорогих параметрів перевантажує endpoint, списки форуму чи вхід. | Rate limiting, валідація довжини й розміру, пагінація, обмеження дорогих пошуків, моніторинг навантаження. |
| P2: Process — Laravel Web Application | S, E | Недостатня перевірка сесії/ролі дозволяє виконувати чужі або адміністративні операції. | Middleware плюс Policy/Gate або еквівалент для кожної операції; відмова за замовчуванням; PHPUnit negative tests. |
| P2: Process — Laravel Web Application | T | SQL injection, mass assignment або неправильна обробка вводу змінює дані поза дозволеною бізнес-операцією. | Eloquent/параметризовані запити, Form Request/Validator, allowlist полів, DB constraints, code review. |
| P2: Process — Laravel Web Application | I | Debug-відповідь, виняток або лог розкриває SQL, stack trace, секрети чи дані іншого користувача. | `APP_DEBUG=false` у production, загальні зовнішні помилки, контроль виводу/логів, тестування відмов. |
| P2: Process — Laravel Web Application | D | Вичерпання процесів, пам'яті або з'єднань БД через надмірні запити чи невалідний контент. | Ліміти вводу, таймаути й rate limit на відповідному рівні, індекси, пагінація, тестування навантаження за потреби. |
| P3: Process — Authentication | S, I | Перебір паролів, перерахування акаунтів або неналежно захищений reset-токен призводить до захоплення акаунта. | Rate limit, нейтральні повідомлення, обмеження строку та повторного використання токена, безпечні password broker налаштування; reset-функцію підтвердити. |
| P3: Process — Authentication | T, E | Звичайний користувач змінює `role`, `is_admin` або інший захищений атрибут через форму профілю. | Масове присвоєння за allowlist, окремий адміністративний сценарій, серверні дозволи, feature tests. |
| P4: Process — Forum / Content | T, I | Stored XSS через тему/допис; несанкціоноване редагування або читання чужого/прихованого контенту. | Екранування шаблонами, санітизація allowlist лише за потреби HTML, перевірки власності, тести на зловмисний вміст і IDOR. |
| P4: Process — Forum / Content | D | Спам, дуже довгі дописи або масові запити погіршують доступність форуму. | Обмеження довжини/частоти, пагінація, індекси; CAPTCHA чи модераційна черга — лише якщо виправдані та реалізовані. |
| P5: Process — Administration | E, T | Обхід адміністративного контролю дозволяє підняти роль, заблокувати користувача або змінити контент без дозволу. | Центральна перевірка привілеїв на сервері, окремі Policies, аудит критичних дій, негативні feature tests. |
| P5: Process — Administration | R, I | Адмін-журнал не містить суттєвих подій або показує надмірні персональні дані. | Визначити мінімальний склад аудиту, доступ за роллю й правила зберігання; перевірити відсутність секретів. |
| D1: Data Store — PostgreSQL | T | Несанкціонована модифікація або видалення користувачів, ролей, тем, дописів чи документації. | Мінімальні права DB-користувача, параметризовані запити, constraints, транзакції, контроль доступу до DB та резервні копії. |
| D1: Data Store — PostgreSQL | I | Відкритий порт БД, надмірні права або витік дампа розкриває набір даних. | Обмежити мережевий доступ, окремі DB-облікові записи, захищене зберігання дампів, ротація секретів у разі витоку. |
| D1: Data Store — PostgreSQL | D | Важкі запити, блокування або вичерпання з'єднань роблять сайт недоступним. | Індекси й аналіз запитів, ліміти/таймаути, транзакції з контрольованою тривалістю, моніторинг і перевірене відновлення. |

## 6. Реєстр пріоритетних сценаріїв загроз

Оцінка є попередньою якісною оцінкою, а не результатом тестування. Рівень потрібно підтвердити після перевірки фактичної експозиції, існуючих захистів і наслідків для бізнесу.

| ID | Сценарій | Початковий ризик | Потрібні контролі | Критерій закриття |
|---|---|---|---|---|
| TM-01 | Звичайний користувач отримує адміністративні привілеї через прямий HTTP-запит або підроблене поле ролі | Критичний | Серверна перевірка ролей/дозволів, allowlist полів, захищені маршрути, аудит критичних дій | PHPUnit feature tests доводять відмову в підвищенні привілеїв усіма перевіреними шляхами. |
| TM-02 | Користувач змінює або видаляє чужу тему/допис, підбираючи ID (IDOR/BOLA) | Високий | Перевірка власності й дозволів на конкретному ресурсі, відповідні Policies/Gates | Тести власника, стороннього користувача, модератора й анонімного користувача відповідають матриці доступу. |
| TM-03 | Зловмисний форумний контент виконується в браузері інших відвідувачів (stored XSS) | Високий | HTML-екранування; перевірена санітизація, якщо дозволений HTML; тестування контенту | Небезпечний ввід відображається як текст або проходить затверджену санітизацію; є regression tests. |
| TM-04 | Перебір паролів або захоплення сесії відкриває доступ до акаунта | Високий | Rate limit, безпечні cookies/HTTPS, регенерація сесії, безпечне завершення сесії | Негативні тести rate limit і сесій; production-конфігурацію перевірено. |
| TM-05 | SQL injection або неконтрольований запит змінює/розкриває дані | Високий | Eloquent/параметризовані запити, валідація, review, найменші DB-привілеї | Перевірені запити та тести для точок, що використовують динамічний ввід. |
| TM-06 | Секрет потрапляє до Git, JavaScript bundle, логу або резервної копії | Високий | Secret management, виключення `.env`, перевірки секретів, мінімізація логів | Артефакти й репозиторій перевірені; виявлені секрети ротовано та вилучено з активного використання. |
| TM-07 | Перевантаження публічного endpoint або форуму погіршує доступність | Середній/високий | Rate limit, межі розміру, пагінація, індекси, спостереження за навантаженням | Існують ліміти; тестами перевірено відмову від надмірного вводу та пагінацію. |
| TM-08 | Скомпрометована або вразлива залежність потрапляє до production | Високий | Перевірка залежностей, lock-файли, review змін, контроль доступу до збірки | Залежності перевіряються на вразливості до релізу, критичні знахідки не залишаються без рішення. |
| TM-09 | Production debug/error response розкриває внутрішні дані | Середній/високий | Вимкнений debug, контрольована обробка винятків, редагування логів | Перевірка конфігурації й тестові помилки не розкривають стек, SQL чи секрети. |
| TM-10 | Підроблення або видалення аудиту ускладнює розслідування адміністративного зловживання | Середній | Контрольований аудит критичних дій і обмежений доступ до записів, якщо аудит затверджено | Є тестовані події для критичних операцій; звичайний користувач не може змінювати журнал. |

## 7. Модель зловмисника

Розглядаються такі можливості атакувальника:

- анонімний користувач, який може надсилати довільні HTTP-запити до публічних endpoint;
- звичайний користувач, що намагається вийти за межі власних прав або отримати доступ до чужого контенту;
- користувач із викраденими обліковими даними чи сесією;
- зловмисник, який надсилає шкідливий текст, URL або параметри форми;
- зловмисник, який намагається перевантажити публічні endpoint;
- постачальник/пакет із компрометованою залежністю або особа, яка отримала надмірний доступ до репозиторію.

Ця модель не припускає, що атакувальник уже має shell-доступ до production-сервера або фізичний доступ до БД. Такі сценарії потребують окремої інфраструктурної моделі загроз.

## 9. Пріоритизація та реагування

- **Критичний ризик:** можливість захоплення адміністративного доступу, довільного виконання коду, масового витоку даних або повного обходу authorization. Блокує реліз і потребує негайної ескалації відповідальному за безпеку/власнику проєкту.
- **Високий ризик:** експлуатація з істотним впливом на дані чи акаунти за реалістичних передумов. Усувається до релізу або потребує формального прийняття ризику та компенсуючих заходів.
- **Середній ризик:** локалізований вплив або складніші умови експлуатації. Реєструється, планується та повторно оцінюється.
- **Низький ризик:** обмежений вплив; виправлення планується з урахуванням вартості й сукупного ризику.

Для підтвердженої експлуатації необхідно оцінити не лише виправлення коду, а й ротацію секретів, анулювання сесій, аналіз логів, відновлення даних і потребу повідомлення зачеплених сторін. Конкретний процес реагування на інциденти рекомендовано оформити окремо.

## 10. Відкриті питання для фіналізації

Перед затвердженням моделі потрібно перевірити:

- фактичні маршрути та middleware для Authentication, Forum і Administration;
- реальну модель ролей: окремі ролі `User`/`Moderator`/`Administrator`, permissions або простіший механізм;
- використовуваний session driver, cookie-параметри, rate limiting і процедуру відновлення пароля;
- чи дозволено HTML у дописах, чи існують вкладення або зовнішні посилання з розширеною обробкою;
- фактичну схему PostgreSQL, права облікового запису застосунку, зовнішню доступність БД і резервне копіювання;
- чи налаштовані пошта, CAPTCHA, аналітика, API, черги, моніторинг, WAF або CI/CD;
- де зберігаються секрети й логи, хто має доступ до них і як довго вони зберігаються;
- які перевірки автоматично виконуються перед релізом.

Після відповіді на ці питання слід позначити кожну загрозу як актуальну, умовну або непридатну, уточнити оцінку ризику й за потреби створити `security_requirements.md` зі стабільними ідентифікаторами вимог.
