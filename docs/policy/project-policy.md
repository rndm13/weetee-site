## Правила зміни політики

- Політика не змінюється побічно в межах звичайної задачі: для зміни створюється окрема задача або чітко відокремлений pull request.
- Зміни погоджуються з власником проєкту або відповідальним технічним керівником.
- Зміна політики фіксується окремим комітом із префіксом `[POLICY]`; версія документа збільшується.
- Якщо чинний код не відповідає політиці, відхилення фіксується в задачі або `tech_notes.md` відповідного модуля із зазначенням ризику та плану усунення. Сам факт наявності старого коду не скасовує вимог для нового коду.

## 1. Скоуп

Політика поширюється на код вебзастосунку, конфігурацію, міграції БД, ресурси фронтенду, автоматизовані тести й документацію, що супроводжується в репозиторії. Вона обов'язкова для всіх, хто змінює проєкт.

Функціональні області порталу:
- **Авторизація та облікові записи** — реєстрація/вхід, завершення сесії, керування обліковими даними та станом облікового запису відповідно до фактично ввімкнених функцій.
- **Форум** — теми, дописи, взаємозв'язки між ними, доступ користувачів і модерація.
- **Адміністрування** — адміністративні операції, керування ролями/правами та контроль модерації в межах наданих повноважень.
- **Опис і документація ПЗ** — публічний інформаційний контент. Якщо для нього існує окремий модуль, він має бути внесений до реєстру модулів; у цьому комплекті він є контекстом сайту, а не окремим детально описаним модулем.

## 3. Фундаментальні принципи

- **Чіткі межі відповідальності.** Контролер приймає HTTP-запит і формує відповідь; валідація запиту відокремлена від бізнес-правил; складні сценарії оформлюються сервісом або action-класом; Eloquent-модель не повинна ставати місцем для всіх правил застосунку.
- **SOLID і зрозумілий код.** Не дублювати однакові правила в контролерах, шаблонах і завданнях черги. Спільну поведінку виносити лише тоді, коли для неї є стабільна відповідальність.
- **Laravel conventions без зайвих абстракцій.** Використовувати штатні механізми Laravel, якщо вони покривають потребу. DDD, CQRS, репозиторії або окремі доменні шари вводити тоді, коли це дає конкретну користь і не дублює Eloquent/контейнер фреймворку.
- **Авторизація на сервері.** Приховування кнопки в UI не вважається контролем доступу. Кожна захищена операція перевіряється через middleware, Gate/Policy або еквівалентний централізований механізм.
- **Мінімальні привілеї.** Користувач, модератор і адміністратор мають лише ті можливості, які потрібні для їхніх задач. Підвищення ролі не повинно бути доступним звичайному користувачеві.
- **Безпечні значення за замовчуванням.** Усі вхідні дані вважаються недовіреними; доступ до ресурсів перевіряється на сервері; секрети зберігаються поза репозиторієм.
- **Схема БД — частина коду.** Структура таблиць, індекси, зовнішні ключі та обмеження змінюються міграціями й перевіряються тестами.
- **Документація має відповідати системі.** Якщо змінюється поведінка модуля, одночасно оновлюються опис бізнес-логіки та журнал змін.

## 4. Архітектура та структура Laravel-застосунку

Застосунок використовує типовий каркас Laravel. Конкретні каталоги можуть відрізнятися залежно від поточного репозиторію, але межі відповідальності мають зберігатися.

| Область                              | Відповідальність                                                                                                               |
|---                                   |---                                                                                                                             |
| `routes/`                            | Маршрутизація та прив'язка до контролерів/middleware; складні правила сюди не виносяться.                                      |
| `app/Http/Controllers/`              | HTTP-рівень: координує запит, викликає потрібну операцію, повертає view/redirect/JSON.                                         |
| `app/Http/Requests/`                 | Правила валідації та авторизації конкретного типу запиту, якщо використовується Form Request.                                  |
| `app/Models/`                        | Eloquent-моделі, зв'язки, касти та вузькі правила, тісно пов'язані зі станом моделі.                                           |
| `app/Policies/` або `app/Providers/` | Політики доступу, Gates та конфігурація механізмів Laravel.                                                                    |
| `app/Services/`                      | Складні або повторно використовувані сценарії бізнес-операцій. Не створювати сервіс лише заради перенесення одного рядка коду. |
| `database/migrations/`               | Версійовані зміни схеми PostgreSQL.                                                                                            |
| `resources/`                         | Blade-шаблони, стилі, JavaScript та інші вихідні frontend-ресурси, що збираються Vite.                                         |
| `tests/`                             | Unit-, feature- та інтеграційні тести, організовані за поведінкою або модулем.                                                 |
| `docs/`                              | Політика, реєстр модулів, бізнес-логіка та технічні нотатки.                                                                   |

Залежності спрямовуються від HTTP-рівня до сценаріїв застосунку й моделей/контрактів даних. Моделі не повинні залежати від контролерів або Blade-шаблонів. Не слід переносити Laravel у власний «фреймворк» без обґрунтованої потреби.

### Загальні межі модулів

- **Authentication** володіє життєвим циклом облікового запису, перевіркою облікових даних і станом доступу. Він не володіє змістом дописів.
- **Forum** володіє категоріями (якщо вони є), темами, дописами та правилами їх життєвого циклу. Він використовує ідентифікатор автора й перевірку прав, але не реалізує власний механізм паролів.
- **Administration** володіє адміністративними сценаріями та правилами привілеїв. Власником даних тем/дописів залишається Forum; адміністративні дії викликають відповідні операції форумного модуля.
- Міжмодульний доступ виконується через публічні методи, політики або добре визначені контракти, а не шляхом дублювання бізнес-правил.

## 5. Політика неймінгу та стилю PHP

- Класи, інтерфейси, трейти й enum-и використовують `PascalCase`; методи та змінні — `camelCase`; константи — `UPPER_SNAKE_CASE`.
- Назви мають відображати предметну область та дію: `CreateTopic`, `UpdatePost`, `BanUser` замість абстрактних `HandleData` або `DoAction`.
- Файли класів узгоджуються з PSR-4/Composer autoload і домовленостями Laravel.
- Вхідні масиви даних не повинні безконтрольно передаватися в `Model::create()` або `update()`. Застосовується валідація й контроль mass assignment (`$fillable`/`$guarded`) відповідно до моделі загроз.
- Використовувати строгі порівняння там, де важливий точний тип або значення. Не придушувати помилки оператором `@`.
- PHPDoc обов'язковий для публічних методів зі складним контрактом, нестандартними типами, нетривіальними обмеженнями або очікуваними винятками. Документація має пояснювати призначення та контракт, а не повторювати очевидний код. Для простих методів пріоритет — нативна типізація й читабельність.

## 6. Валідація, помилки й обробка винятків

- Валідація структури HTTP-вводу виконується Form Request або валідатором Laravel. Бізнес-інваріанти перевіряються також під час виконання операції та, де доречно, обмеженнями БД.
- Невалідний ввід повертає контрольовану помилку, зрозумілу формі/UI або API-клієнту; внутрішні стеки, SQL, токени й секрети користувачам не показуються.
- Не перехоплювати `Throwable` без потреби. Якщо виняток перехоплюється, він має бути належно оброблений, перетворений у відповідь або записаний у журнал без конфіденційних даних.
- Операції, що мають змінювати кілька пов'язаних записів атомарно, виконуються в транзакції БД.
- Конфлікти унікальності та конкурентні зміни обробляються контрольовано; перевірка на рівні застосунку не замінює UNIQUE constraint.

## 7. Дані та PostgreSQL

- Усі зміни схеми — через міграції. Міграції мають бути послідовними, відтворюваними та сумісними з даними, які потрібно зберегти.
- Використовувати зовнішні ключі для реальних залежностей і індекси для полів, за якими часто шукають, фільтрують або сортують.
- Унікальність облікового запису (наприклад, нормалізованої email-адреси) має бути забезпечена узгодженими правилами в застосунку й у БД, якщо email є ідентифікатором входу.
- Видалення користувачів, тем і дописів має мати явно визначену семантику: фізичне видалення, soft delete, анонімізація або блокування. Випадкове каскадне видалення змісту неприпустиме.
- Для пагінації форумних списків використовувати пагінацію Laravel та відповідні індекси; не завантажувати всі теми/дописи без межі.
- Секрети, паролі та токени не зберігаються у відкритому вигляді. Паролі зберігаються тільки через безпечний хешер Laravel; механізм відновлення доступу має використовувати одноразові або обмежені в часі токени згідно з конфігурацією Laravel.

## 8. Безпека й авторизація доступу

- Усі мутаційні запити, що змінюють стан вебсесії, захищаються штатним CSRF-механізмом Laravel, якщо це застосовно до типу клієнта.
- Виведення користувацького тексту в HTML екранується. Сирий HTML дозволяється лише за окремо визначеними правилами санітизації та довіреного використання.
- Для входу, реєстрації, відновлення пароля й інших чутливих операцій застосовується rate limiting та однакова для різних станів облікового запису відповідь там, де це потрібно для запобігання перебору/переліку акаунтів.
- Перевіряються не лише роль, а й доступ до конкретного об'єкта: користувач не може змінювати чи видаляти чужий допис лише тому, що знає його ID.
- Адміністративні маршрути захищаються серверною перевіркою повноважень. Призначення ролі адміністратора не доступне звичайному self-service профілю.
- Журналювання не повинно містити паролів, сесійних cookie, повних токенів або інших секретів.
- Секретні значення зберігаються в `.env`/secret store середовища розгортання; `.env` не комітиться.
- Залежності оновлюються контрольовано, а вразливості та підозрілі повідомлення користувачів/контент обробляються згідно з процесом супроводу проєкту.

## 9. Політика тестування

### Інструмент і рівні

Основний тестовий фреймворк — PHPUnit. Тести мають перевіряти поведінку застосунку, а не внутрішні деталі реалізації, які можуть безпечно змінюватися.

- **Unit:** ізольовані правила та класи, для яких не потрібен HTTP-стек і БД.
- **Feature:** маршрути, middleware, валідація, автентифікація, авторизація, взаємодія контролерів із моделями та відповіді.
- **Database/integration:** міграції, зв'язки, обмеження, транзакції й запити PostgreSQL. Якщо CI використовує SQLite замість PostgreSQL, відмінності SQL/типів мають бути враховані; критичні для PostgreSQL сценарії потрібно тестувати на PostgreSQL.

### Мінімальні вимоги до сценаріїв

- Успішний сценарій і негативні випадки (некоректні дані, відсутня сесія, недостатні права, неіснуючий ресурс, конфлікт стану).
- Авторизація: анонімний користувач не виконує захищені дії; звичайний користувач не отримує адміністративні права; власник ресурсу та сторонній користувач мають різні дозволи там, де це задумано.
- Форум: перевірка створення/редагування, належності допису до теми, правил блокування/закриття теми та модерації, якщо ці функції ввімкнені.
- Адміністрування: заборонений доступ без привілеїв; спроби підвищити власну роль звичайним користувачем відхиляються.
- Не використовувати зовнішні реальні сервіси в unit-тестах. Для пошти, черг і зовнішніх інтеграцій використовувати фейки/моки Laravel або ізольоване тестове середовище.
- Тести не повинні залежати від порядку запуску або даних, залишених попереднім тестом.

## 10. Git Workflow та контроль якості

- Кожна зміна має бути пов'язана із задачею або чітким описом мети.
- Перед злиттям запускаються PHPUnit-тести та налаштовані перевірки форматування/статичного аналізу. Перелік фактично налаштованих CI-команд фіксується в README або конфігурації CI.
- Зміни міграцій, permission checks і бізнес-інваріантів проходять code review з особливою увагою до зворотної сумісності й безпеки.
- Рекомендований формат комітів: `[тип] короткий опис`, де типом можуть бути `FEAT`, `FIX`, `TEST`, `DOCS`, `POLICY`, `REFACTOR`.
- Секрети, локальні дампи БД, логи з персональними даними та зібрані артефакти середовища не комітяться без явної потреби.

|---:|---                                     |---                                                                                                    |
| 1  | Товстий контролер                      | Бізнес-правила, перевірки прав і багатокрокові операції зібрані в контролері.                         |
| 2  | Лише UI-авторизація                    | Посилання/кнопку приховано, але endpoint не перевіряє дозволи.                                        |
| 3  | Надмірна довіра до вводу               | HTTP-поля або вміст допису зберігаються без валідації чи небезпечний HTML виводиться без екранування. |
| 4  | Mass assignment без контролю           | У модель масово передаються неперевірені поля, включно з роллю/статусом.                              |
| 5  | Паролі або токени у відкритому вигляді | Облікові дані або секрети зберігаються чи журналюються без захисту.                                   |
| 6  | Бізнес-правила дублюються              | Однакова логіка розходиться між контролером, моделлю, шаблоном та адміністративним endpoint.          |
| 7  | Немає обмежень БД                      | Унікальність і цілісність покладаються лише на перевірку перед записом.                               |
| 8  | Happy-path-only                        | Тестуються лише успішні сценарії без перевірки відмов доступу та некоректних даних.                   |
| 9  | Неконтрольоване адміністрування        | Звичайний користувач може призначити собі роль або обійти перевірку ролі прямим HTTP-запитом.         |
| 10 | Застаріла документація                 | Опис стверджує, що функція існує, хоча код її не реалізує, або навпаки.                               |
