# Authentication — BUSINESS LOGIC

> Документ визначає концептуальну модель модуля автентифікації та облікових записів. Він підготовлений за шаблоном, але без перегляду вихідного коду. Назви сутностей і поля нижче є логічною моделлю. Пункти щодо реєстрації, верифікації email, відновлення пароля та деактивації потрібно підтвердити за фактичними маршрутами й конфігурацією Laravel.

## Purpose

Модуль `Authentication` володіє:

- ідентичністю облікового запису та атрибутами, потрібними для входу;
- перевіркою облікових даних, входом/виходом і життєвим циклом вебсесії через штатний механізм Laravel;
- зміною пароля та відновленням доступу, якщо ці функції ввімкнені;
- станом облікового запису, який впливає на можливість входу (наприклад, активний/заблокований/видалений — конкретні стани потребують звірки з кодом);
- ідентифікацією користувача для інших модулів через стабільний ID.

**NOT here:**

- перевірка дозволу редагувати конкретну тему чи допис — `Forum` і його Policy;
- призначення адміністративних ролей і виконання адміністративних дій — `Administration`;
- створення та редагування документації ПЗ — модуль документації/контенту.

## Entities

| Entity | Basic Fields | Description | Invariants |
|---|---|---|---|

Фактичні назви та склад полів визначаються моделлю і міграціями Laravel. | ID стабільний після створення. Якщо email є ідентифікатором входу, його нормалізоване значення унікальне. ## Облікові дані й інваріанти

- Перевірка пароля виконується штатним механізмом хешування Laravel; самостійний криптографічний алгоритм для паролів не реалізується.
- Додавання чи оновлення облікового запису приймає лише дозволений набір полів. Клієнт не може передати довільно `role`, `is_admin`, `status` чи інше привілейоване поле, якщо воно не дозволене конкретним серверним сценарієм.
- Повідомлення про невдалий вхід не повинно розкривати, чи існує конкретний email/username, якщо це створює ризик переліку облікових записів.
- Вхід має бути обмежений за частотою спроб. Після успішної автентифікації сесія повинна оброблятися відповідно до рекомендацій Laravel щодо захисту від session fixation.
- Після зміни пароля старі сесії або токени мають оброблятися за задокументованою політикою безпеки. Якщо поточна реалізація цього не робить, це слід зафіксувати як ризик, а не приховувати в документації.

## Status Lifecycle

Цільова модель станів, яку потрібно підтвердити:

| Поточний стан | Дія | Наступний стан | Умова |
|---|---|---|---|
| `PENDING` | Підтвердження облікового запису | `ACTIVE` | Лише якщо продукт вимагає підтвердження email/облікового запису |
| `ACTIVE` | Адміністративне блокування | `BLOCKED` | Дозволено лише уповноваженій ролі |
| `BLOCKED` | Розблокування | `ACTIVE` | Дозволено лише уповноваженій ролі |
| `ACTIVE` / `BLOCKED` | Видалення або деактивація | `DEACTIVATED` | Повне видалення даних про користувача, включно з публікаціями та коментарями |

## Ключовий флоу: вхід

1. Користувач надсилає обліковий ідентифікатор і пароль через HTTPS у production-середовищі.
2. Laravel валідує формат вводу, обмежує частоту спроб і перевіряє облікові дані.
3. Перевіряється доступність облікового запису, якщо застосунок має відповідний стан або обмеження.
4. Успішна автентифікація створює/оновлює сесію через налаштований guard.
5. Користувач перенаправляється на дозволену сторінку; адреса перенаправлення не повинна дозволяти відкритий redirect на довільний зовнішній сайт.
6. Наступні захищені запити використовують сесію та серверні перевірки дозволів.

**Boundary:** модуль підтверджує, хто користувач; він не гарантує, що користувачу можна змінювати кожен конкретний ресурс.

## Ключовий флоу: відновлення пароля

1. Користувач подає адресу облікового запису.
2. Відповідь не розкриває зайвої інформації про існування акаунта.
3. Сервер створює обмежений у часі токен за механізмом Laravel і відправляє інструкцію через налаштований канал.
4. Токен перевіряється перед дозволом встановити новий пароль.
5. Пароль хешується; токен стає непридатним для повторного використання відповідно до механізму password broker.

Цей флоу описує цільову поведінку, а не підтверджену наявність налаштованої поштової доставки.

## Domain Policies / правила доступу

| Правило | Призначення |
|---|---|
| Вхід лише з валідними обліковими даними | Перевірка через Laravel Auth/guard; паролі не порівнюються вручну як звичайний текст. |
| Обмеження спроб входу | Rate limiting для зниження ризику перебору. |
| Заборона привілейованих полів у звичайному профілі | Зміна ролей/адміністративного статусу виконується окремим привілейованим сценарієм. |
| Заборона входу неактивному акаунту *(за наявності статусів)* | Перевірка сервером до створення авторизованої сесії. |

## Application Commands & Queries — концептуальні операції

**Commands:**

| Операція | Призначення |
|---|---|
| `RegisterAccount` | Створити обліковий запис після валідації дозволених полів. |
| `AuthenticateUser` | Перевірити облікові дані й відкрити сесію. |
| `LogoutUser` | Завершити поточну сесію. |
| `ChangePassword` | Змінити пароль після перевірки необхідних умов. |
| `RequestPasswordReset` | Запустити й завершити процес відновлення доступу. |

**Queries:**

| Операція | Призначення |
|---|---|
| `GetCurrentUser` | Повернути мінімальний набір даних поточного користувача, потрібний інтерфейсу. |
| `GetAccountStatus` | Повернути стан акаунта без розкриття облікових секретів. |

Це назви бізнес-операцій для документації, а не вимога створювати класи з такими іменами.

## Infrastructure

- Laravel Auth/guards і middleware відповідають за сесію та перевірку автентифікації.
- Eloquent-модель і PostgreSQL зберігають поля облікового запису згідно з фактичними міграціями.
- Password broker, кеш/сховище токенів і доставка листів використовуються лише якщо їх налаштовано.
- Фронтенд на Vite відповідає за клієнтські ресурси форми, але не є місцем перевірки справжності чи прав доступу.

## Security and privacy

- Не записувати пароль, повний токен відновлення, cookie або session ID у прикладні логи.
- Видавати назовні лише потрібні користувачу атрибути. Парольний хеш, токени й службові поля не потрапляють до представлень чи JSON-відповідей.
- Приватні маршрути захищаються middleware і додатковими policies на рівні ресурсу.

## Tests

Мінімальні сценарії PHPUnit:

- успішний/невдалий вхід і вихід;
- некоректні вхідні дані та перевищення rate limit;
- захищена сторінка недоступна неавтентифікованому користувачу;
- недоступні для mass assignment поля не змінюються через профільну форму;
- відновлення пароля, термін дії та одноразовість токена — якщо функція існує;
- заблокований/неактивний користувач не може ввійти — якщо такі стани передбачені.
